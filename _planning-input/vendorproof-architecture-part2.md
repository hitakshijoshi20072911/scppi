## 7. Swytchcode API architecture and method-verification plan

### 7.1 Execution model

Decision: one server-side executor module is the only code in the system that can invoke Swytchcode. \[Proposed\]

| Option | Description | Verdict |
| --- | --- | --- |
| A. JS/TS runtime SDK on our server | Thin wrapper that runs the CLI; binary must be on the same machine \[Docs, secondary\] | Use, but only inside the executor module |
| B. Spawn swytchcode exec directly, argument array, never a shell string | No SDK dependency; same trust model | Fallback if the SDK fails the Milestone 2 check |
| C. Swytchcode or provider calls from browser code | Exposes credentials | Forbidden |
| D. Windsurf MCP in production | MCP is a developer tool in the editor | Development only |
| E. Direct provider SDKs or REST calls | Bypasses the trusted tool list | Forbidden unless a decision record exists |

Executor rules (src/swytchcode/executor.ts):

1. Accepts only a canonical ID that is on a code-level allowlist generated from verified methods in docs/api-inventory.md. Anything else throws before any process starts.
2. Validates input with a Zod schema derived from the Wrekenfile input schema, and validates the parsed output the same way. Exit code zero is never treated as success on its own.
3. Adds what the SDKs do not: a hard timeout, a concurrency limit per provider, a typed error class, secret redaction, and a correlation ID.
4. Writes a provider\_execution row as pending before the call and finalises it after, storing request\_hash and a response summary, never secrets or full client text.
5. Never retries a write. Retry policy lives in section 12.
6. Is injected into adapters as an interface so tests can substitute a fake.

Guardrail: a CI check fails any pull request that changes .swytchcode/tooling.json, manifest.json or policies.json unless docs/api-inventory.md changes in the same pull request and a human code owner approves. An AI agent proposes; it never enables a tool on its own.

### 7.3 Authentication planes and tenant selection

- Local development: swy login device flow, provider accounts connected with swy auth connect against sandbox or test accounts only.
- Server: SWYTCHCODE\_TOKEN as a process environment secret; provider credentials supplied as environment variables from the secret manager, which is first in the documented resolution order. The encrypted managed store is not relied on in containers because a container filesystem is ephemeral. \[Proposed, inferred\]
- Tenant selection (Blocker B1): whether one server process can run a call with a different provider credential per workspace is not established. Release one therefore runs in single-tenant mode: one workspace, one provider account per provider, credential names resolved from server configuration. The workspace ID always comes from the authenticated session and is never read from a query string, header or body.
- Gate before a second workspace is enabled: B1 answered from primary documentation or by a recorded experiment, plus an automated test proving workspace A can never execute with workspace B's credential.

### 7.4 Sandbox versus deployment environment

The tooling.json mode (sandbox) is a Swytchcode setting. It is not the deployment environment of the web app, and it does not by itself prove that a provider key is a test key.

- The app has its own APP\_ENV (development, staging, production).
- At startup, a financial adapter refuses to run if APP\_ENV is not production and the configured Stripe key does not carry the test-mode prefix, or if it is production and the key does.
- Production APIs are never the default test target (section 13).

### 7.5 Method-verification procedure

Run by you in Windsurf at Milestone 2, one provider at a time. Commands come from the CLI README and must be confirmed with swy --help on CLI 2.25.1 before use. Do not run any of this until the architecture is approved.

1. Re-read the primary pages on docs.swytchcode.com that could not be opened in this session. Record exact findings in docs/verified-facts.md with URL and date. Resolves B3.
2. Rung 1: catalogue mention at swytchcode.com/apis. Record the screenshot or text.
3. Rung 2: swy search for the provider. Record the real output as \[CLI\].
4. Rung 3: swy get for the provider. Confirm tooling.json is unchanged afterwards, as documented.
5. Rung 4: swy list and swy info to see the methods actually present. Delete any planned operation that is not present.
6. Rung 5: read each needed method's canonical ID, input schema and output schema from the Wrekenfile. Copy them verbatim into docs/api-inventory.md.
7. Rung 6: swy add for only the minimum methods needed, then swy check.
8. Rung 7: connect the sandbox or test account with swy auth connect, then swy auth status.
9. Rung 8: swy exec with --dry-run, then a real call against sandbox data, then record the output.
10. Only then generate the Zod schemas and add the ID to the executor allowlist.

A provider counts at the highest rung actually reached, and nothing above it may be claimed.

### 7.7 Financial provider selection rule

Choose the first provider, in the order Stripe then QuickBooks Online, that reaches rung 8 for all of: create a draft invoice with line items; read the invoice back with status and total; send or record a stable identifier so the draft can be found later; and an idempotency mechanism if one exists. Stripe is preferred because it is evidenced in the catalogue and has a test mode; that preference is not a verification. If neither passes, the documented blocker is a manual invoice export, with the approval and audit trail unchanged.

## 8. Security architecture and threat model

Swytchcode governs calls that pass through its execution layer. Everything else in the table below is the application's responsibility. \[Proposed\]

### 8.1 Authentication, sessions and authorisation

| Control | Design |
| --- | --- |
| Login | Maintained auth library confirmed at Milestone 1 (passwordless email link or OAuth preferred over home-built passwords); if passwords are used, argon2id. \[Approve\] |
| Session | Opaque ID in a server-side Postgres session table; cookie is HttpOnly, Secure, SameSite=Lax, \_\_Host- prefixed, no Domain attribute; ID rotated on login and privilege change |
| Lifetime | Idle expiry 12 hours, absolute expiry 7 days; approval requires authentication within the last 15 minutes. \[Approve\] |
| CSRF | SameSite plus a per-session token in a custom header on every mutating request, plus Origin check on the server |
| Sign-out | Deletes the session row; membership removal deletes all that user's sessions at once |
| Authorisation | Checked on the server per request from the database, never from claims cached in the browser |
| Resource checks | Every repository function takes a WorkspaceContext built from the session; there is no function that fetches by ID alone |

Role permissions:

| Action | Owner | Admin | Member |
| --- | --- | --- | --- |
| Manage members and workspace settings | Yes | No | No |
| Connect or disconnect providers | Yes | Yes | No |
| Create clients, projects, contracts | Yes | Yes | No |
| Enter time entries | Yes | Yes | Yes |
| Approve time entries and milestones | Yes | Yes | No |
| Start a billing run, review items | Yes | Yes | Yes |
| Approve a billing run for invoicing | Yes | No | No |
| Read audit log and reports | Yes | Yes | Own runs only |

Separation of duties: in a solo workspace the owner will approve their own time entries and run. The UI records this as self-approved and the report states it. \[Approve\]

### 8.2 Tenant isolation

1. Session resolves to exactly one workspace per request.
2. Repositories add workspace\_id to every query and every insert. Composite (workspace\_id, id) foreign keys, as in section 5, stop cross-workspace references at the schema level.
3. Row-level security in Postgres is the second layer, driven by a per-transaction setting. The application role is not the table owner and cannot bypass it.
4. A lint rule forbids importing the database client outside src/db and repositories.
5. Unknown or other-workspace IDs return 404, not 403, so existence is not disclosed.

### 8.3 Secrets

- No secret in source, frontend variables, logs, error bodies, prompts or the database. Only variable names appear in .env.example.
- Secrets live in the host secret manager and are injected as environment variables. Separate values for staging and production; Stripe test key only outside production.
- pino redaction list covers authorization headers, cookies, tokens and any field named secret, key or token. A unit test asserts redaction.
- Secret scanning runs as a pre-commit hook and in CI. You are never asked to paste a secret into any AI chat.
- Rotation: documented in docs/production.md; the Swytchcode token and each provider credential have an owner and a rotation date.

### 8.4 API and web controls

| Area | Control |
| --- | --- |
| Validation | Zod schema on every route body, query and parameter; unknown keys rejected |
| Size and rate | Body limit 256 KB except none accepting files in release one; per-IP and per-session rate limits; stricter on login and approve |
| CORS | None needed if frontend and API share one origin behind a reverse proxy (section 19); otherwise an exact-origin allowlist, never a wildcard with credentials |
| Headers | CSP without unsafe-inline for scripts, HSTS, X-Content-Type-Options, frame-ancestors none, Referrer-Policy; HTTPS only |
| Output encoding | React escapes by default; no raw HTML rendering of provider text; PDF is built from text drawing calls, not HTML |
| SQL injection | Parameterised queries only through the ORM; no string-built SQL |
| SSRF | The server never fetches a URL supplied by a user or found in provider content; provider URLs are displayed as links only |
| Path traversal | No user-controlled file paths; report names are generated |
| Webhooks | None accepted in release one; when added, section 10 rules apply |
| Dependencies | Lockfile committed, exact versions, audit in CI, install scripts disabled except an allowlist |

### 8.5 External content and prompt injection

All text from GitHub, Linear, commits, comments and descriptions is untrusted data.

1. The classifier has no tools, no network access, no database access and no secrets. It returns one JSON object per item and nothing else.
2. Output schema: item ID (must match an item sent), category (an enum built from that contract's scope\_rule categories plus unclear), confidence (low, medium, high), a short reason, a client-friendly description. No field exists for hours, amounts or status.
3. The prompt places instructions first, wraps each item's text in clearly delimited data blocks, and states that text inside them is never an instruction.
4. The backend rejects any output that fails the schema, names a category not in the contract, references an unknown item ID, or exceeds length limits. One retry, then the item becomes needs\_review.
5. Output is always stored as ai\_suggestion and displayed as plain text. A human action is the only thing that sets an item to approved.
6. A dedicated injection test corpus (section 13) must pass before Milestone 5 closes. Passing it is evidence of resistance to those cases, not a guarantee.

### 8.6 Data privacy

- Minimisation: store only fields needed for evidence; do not store source code, diffs or private comments.
- LLM disclosure: titles and issue text leave the system to the model vendor. Vendor choice, retention terms and client disclosure wording need your decision. \[Approve\]
- Provider disconnect revokes the credential reference and stops sync; imported evidence for approved runs is kept.
- Account deletion: export, then purge, then state which financial records remain and why (section 5).
- Logs carry IDs, not client names or work text. Screenshots and demos use seeded fake data.

### 8.7 Threat model

| ID | Threat | Control | Proving test |
| --- | --- | --- | --- |
| T01 | Cross-workspace read or write by guessed ID | Scoped repositories, RLS, 404 on miss | Two-workspace suite hits every route |
| T02 | Session theft or fixation | HttpOnly Secure cookie, rotation, revocation | Session reuse after sign-out fails |
| T03 | CSRF on approve or invoice | SameSite, token, Origin check | Request without token rejected |
| T04 | Prompt injection through PR or issue text | Section 8.5 | Injection corpus yields only schema-valid suggestions or needs\_review |
| T05 | Forged inbound Slack callback | Signature and replay checks (section 10) | Bad signature and replayed event rejected |
| T06 | Duplicate invoice | Unique approval, claim key, singleton job, provider key | Concurrent approve and retry tests |
| T07 | Approved content altered before execution | Content hash revalidation | Mutate a line after approval; execution aborts |
| T08 | Secret in logs, errors or prompts | Redaction, scanning, no secrets in prompts | Seeded fake secret never appears in output |
| T09 | AI agent widens the trusted tool list | CODEOWNERS plus CI rule plus executor allowlist | Change without review fails CI |
| T10 | Swytchcode token compromise | Secret manager, separate tokens per environment, rotation | Rotation drill documented |
| T11 | Live Stripe key outside production | Startup assertion | Boot with wrong key refuses |
| T12 | Audit log tampering | Insert-only trigger, no UPDATE or DELETE grant, hash chain | Update attempt raises; chain verification fails on edit |
| T13 | SSRF | No user-supplied fetch | Static check and review |
| T14 | Control characters or markup in PDF text | Text-only rendering, character sanitising | Fixture with hostile strings renders as text |
| T15 | Denial of service through huge imports | Page and item caps, per-workspace job limit | Cap reached produces partial, not a crash |
| T16 | Malicious dependency | Lockfile, exact pins, audit, install scripts off | CI audit gate |
| T17 | Removed member keeps access | Per-request membership check, session purge | Removed user's next request fails |

Residual risk recorded now: a database administrator can still alter any table, so the audit hash chain head is also copied to the private report folder at each approval, which detects tampering but does not prevent it.

## 9. Financial execution and approval model

### 9.1 Amount stages

| Stage | Meaning | Who or what sets it | Can become an invoice? |
| --- | --- | --- | --- |
| estimated | Dashboard preview that includes unapproved evidence | Engine | No |
| proposed | Engine output from approved time entries and milestones | Engine | No |
| approved | Owner approved a frozen version | Human | Yes, once |
| draft\_invoice | Provider draft created and verified | Executor job | Already is one |
| finalised | Invoice finalised or sent | Outside VendorProof in release one | Not applicable |

A stage only moves forward. Any change to an approved amount creates a new proposed version, clears the approval and writes an audit event. A change in AI classification never alters an approved invoice.

Currency scope: release one supports currencies with 0 or 2 minor digits. Three-digit currencies are rejected at contract creation. \[Proposed\]

### 9.2 Confirmation screen

The approval screen shows, from the database and not from the browser: client; project; billing period and time zone; invoice recipient; currency; every line with its evidence (time entry or milestone), minutes or milestone quantity, rate, and amount; visible reduction lines for hour caps and included allowances; subtotal; configured tax line; total; completeness label (complete or partial, with the missing source named); count of items decided by a human versus rule-matched; the audit report version and the first characters of its SHA-256; and a plain statement that only a draft will be created and nothing will be sent or charged.

### 9.3 Approval rules

1. Only an owner can approve. The request must come from an authenticated session that authenticated within the last 15 minutes. \[Approve\]
2. The page loads with a one-time approval token bound to run ID, run version and session. A reused or stale token is rejected.
3. The approval stores content\_hash over the canonical JSON of: ordered lines (evidence ID, minutes, rate, amount, description), recipient, currency, subtotal, tax, total, period, contract snapshot version, and report version with its SHA-256.
4. The approval expires after 24 hours. \[Approve\] Expiry returns the run to ready\_for\_approval.
5. The approver and time are recorded. A self-approval in a solo workspace is labelled as such.
6. The run has to be complete, or partial with an explicit user acceptance recorded earlier. A partial run shows the label on the approval screen and on the report.

### 9.4 Execution sequence

1. Approve call: validates token and version, inserts the approval row, writes an audit event. Unique constraint allows one live approval per run.
2. Claim: one transaction moves the run to creating\_draft, inserts provider\_execution with key invoice:{run\_id}:{approval\_id}, and enqueues the job under the same singleton key.
3. Worker revalidates: recomputes the hash from the database; recomputes every amount with the engine and compares to the stored line amounts; checks the currency, recipient and total are unchanged. Any mismatch aborts, clears the approval and logs why.
4. Pre-flight: financial key matches the environment (section 7.4); total is greater than zero; recipient exists; no invoice\_draft exists for this approval.
5. Write through the adapter and executor, one attempt, with the provider idempotency key and metadata if the verified method supports them.
6. Read back through a verified read method and run the checks in 9.5.
7. Record invoice\_draft, update the run, write the audit event, enqueue the optional Slack notification.

### 9.5 Verification and outcome mapping

| Observed result | Run state | Retry allowed |
| --- | --- | --- |
| Draft read back; status draft; currency, total and line count match | draft\_created | Not needed |
| Provider rejected with a clear validation error and a read confirms no invoice | failed | New approval only, after the cause is fixed |
| Timeout, connection reset, 5xx, or response that cannot be parsed | draft\_unknown | Never resend; lookup by stored metadata or human check |
| Invoice found but status, currency, total or lines differ | draft\_unknown, flagged for human | No |
| Authentication failure | failed, provider marked disconnected | After reconnect, with a new approval |

### 9.6 Never done in release one

Finalise or send an invoice; create a charge, payment link or refund; modify an existing provider invoice; touch any accounting record unrelated to the one draft; run a financial write from a worker job without a persisted approval; let the classifier or any AI agent trigger or approve any of the above.

## 10. Slack interaction architecture

Decision: notification only in release one. The dashboard is the only approval surface. \[Proposed, from your own requirement\]

### 10.1 Release one

- One outbound message when a run reaches ready\_for\_approval, and one when a draft is created or fails.
- Content: run ID, project name, period, counts, a link to the dashboard. No amounts, rates, client names or work-item text unless the owner switches that on. \[Approve\]
- Sent through a verified Swytchcode Slack method (Milestone 7). Failure is recorded and never blocks or alters a run.
- Swytchcode's native approval workflows are not relied on: their plan availability was not retrieved.

### 10.2 If interactive buttons are added later

Slack would call an inbound VendorProof endpoint that Swytchcode does not protect, so the application owns every check. \[Unverified: confirm each against current Slack documentation at Milestone 7\]

| Requirement | Design |
| --- | --- |
| Endpoint | POST /webhooks/slack/interactions, raw body preserved before parsing, no session cookie, excluded from CSRF but not from rate limiting |
| Signature | HMAC-SHA256 over the version string, timestamp and raw body using the Slack signing secret; constant-time compare; reject on mismatch |
| Replay | Reject timestamps outside a 5-minute window; store each action or payload ID in idempotency\_record and reject repeats |
| Identity | Slack user ID is linked to a VendorProof user through an explicit, owner-confirmed link; never matched by email or display name |
| Binding | Action value carries an opaque token that maps to one pending approval row, the workspace and the run version |
| Authorisation | The linked user must still be an owner of that workspace |
| Double approval | Same unique approval constraint as the dashboard |
| Expiry | Token expires with the approval |
| First interactive version | The button is Review, which opens the dashboard approval page. Approving from inside Slack is a later decision. \[Approve\] |

A browser redirect or a button click without these checks is never proof of approval. A new table (webhook\_event) is added only when this is built.

## 11. Google Drive privacy architecture

Decision: the database is the authoritative store of the report; Drive holds a private convenience copy. Drive is never described as immutable or tamper-proof. \[Proposed\]

### 11.1 Report lifecycle

1. The worker renders the PDF with PDFKit from database rows only (never from live provider calls), at ready\_for\_approval.
2. It computes SHA-256, stores bytes, size and hash in report (run\_id, version), and writes an audit event.
3. A new run version produces a new report version. Older versions remain.
4. Upload to Drive happens after the database write, through a verified Swytchcode method, and stores drive\_file\_id.
5. Approval requires a database report, not a successful Drive upload.

### 11.2 Access and naming

| Topic | Decision |
| --- | --- |
| Ownership | The connected Drive account; one private root folder named VendorProof |
| Path | VendorProof/{client-slug}/{project-slug}/{period}/ |
| File name | run-{first 8 of run ID}-v{version}-{first 8 of sha256}.pdf |
| Sharing | No anyone-with-link, no domain-wide sharing, no automatic sharing. Granting access to a named person is a separate human action after the verified permission method is read. |
| Client-visible copy | Not in release one. If added, it is a separately rendered, redacted report with its own version and hash. \[Approve\] |
| Invoice reference | The draft invoice description or metadata carries the report ID and the first characters of the SHA-256, not a Drive link, so an invoice never exposes a private URL |

### 11.3 Integrity verification

- Viewing a report recomputes the hash of the stored bytes and compares it with the recorded one.
- An on-demand check can download the Drive copy and compare. A mismatch is shown as modified outside VendorProof and raises an audit event.
- UI wording: recorded and hash-verified, never immutable or tamper-proof.

Report contents: client, project, period, contract snapshot version, completeness label, every work item with its original provider link, classification source (rule, AI suggestion, or human) and decision, every time entry and milestone, calculations, approver and time, and a list of anything excluded and why.

## 12. Error, retry, timeout and idempotency strategy

### 12.1 Error classes

| Class | Examples | Handling |
| --- | --- | --- |
| validation | Input fails schema | Reject, 422, no provider call |
| auth | Token or credential rejected | Mark provider disconnected, stop writes, tell the owner |
| permission | Provider scope missing | Fail with a specific message; no retry |
| rate\_limit | Provider throttling | Honour any retry-after; back off; run becomes partial if the budget is exhausted |
| timeout | No answer in time | Read: retry. Write: unknown, never resend |
| provider\_5xx | Server error | Read: retry. Write: unknown |
| provider\_4xx | Rejected request | No retry; record summary |
| schema\_mismatch | Output differs from the Wrekenfile schema | Treat as unknown for writes, failed for reads; raise an alert |
| internal | Our bug | Fail the job; keep state consistent through transactions |

### 12.2 Retry rules

| Operation | Policy |
| --- | --- |
| Provider read | Up to 3 attempts, exponential backoff with jitter, cap 20 seconds, only on timeout, 5xx or rate\_limit |
| Provider write without a verified idempotency key | Zero automatic retries |
| Provider write with a verified idempotency key | One retry with the same key, only after a read confirms no draft exists, still preferring human resolution |
| Classification call | One retry on invalid schema or transport error; then needs\_review |
| Job (pg-boss) | Retry only jobs marked safe to repeat (ingest, classify, render); invoice job retry limit is zero |
| Webhook sender side | Not applicable in release one |

Circuit breaker per provider: five consecutive failures within 60 seconds opens the breaker for 60 seconds; reads fail fast with a partial result.

### 12.3 Timeouts and concurrency

Starting values, to be tuned from measurement: provider read 15 seconds; provider write 30 seconds; classification call 45 seconds; ingestion job 10 minutes; report job 2 minutes; invoice job 2 minutes. Concurrency: 4 provider calls at once per provider per workspace, 1 invoice job per workspace, a global worker ceiling set in configuration. Timeouts are enforced by the executor because the SDKs add none. \[Docs\]

### 12.4 Idempotency layers

| Layer | Mechanism |
| --- | --- |
| HTTP | Idempotency-Key header on create-run, approve and cancel calls; stored in idempotency\_record with request\_hash; same key with a different hash returns 409 |
| Approval | Unique (run\_id) where not revoked |
| Claim | Deterministic key invoice:{run\_id}:{approval\_id} on provider\_execution and the singleton job |
| Execution | Persisted pending row before any write; a pending row at startup with no completion is reconciled before new work |
| Provider | Idempotency key and metadata if the verified method accepts them \[Unverified\] |
| Verification | Read back and compare before success is recorded |

### 12.5 Correlation and audit

A correlation ID is created per request, copied into every job, executor call, provider\_execution row, audit event and log line, and returned in error bodies. Audit events are written in the same transaction as the state change they describe, and hash-chained as in section 5.

### 12.6 Rate-limit budget

Third-party pages quote 1,000 execution calls per month on the free tier. \[Unverified\] The design therefore minimises calls: ingest only the billing window; reuse work\_item.content\_hash to skip unchanged items; never poll; one ingest per run unless the user asks to refresh; and a per-workspace monthly call counter derived from provider\_execution so the UI can warn before a run begins.

### 13.2 Billing test vectors (must exist before Milestone 4 closes)

Ties round up. Rate is in minor units.

| Case | Input | Expected |
| --- | --- | --- |
| Round up, 15 minutes | 1, 15, 16 minutes | 15, 15, 30 |
| Nearest, 15 minutes | 7, 8, 22, 23 minutes | 0 (flagged zero-rounded), 15, 15, 30 |
| Nearest, 6 minutes, tie | 3 minutes | 6 |
| Amount, half-up | 15 min at rate 12000 | 3000 |
| Amount, half-up | 1 min at rate 100 | 2 |
| Amount, tie | 1 min at rate 30 | 1 |
| Amount, below tie | 1 min at rate 29 | 0, flagged |
| Period boundary, Asia/Kolkata | Merge at 2026-10-31 18:29:59 UTC versus 18:30:00 UTC for \[Oct 1, Nov 1) | Included versus excluded |
| Daylight saving | 25-hour day on 2026-11-01 in America/New\_York | Items in the repeated hour both belong to that day |
| Hour cap | Entries exceed cap | Reduction appears as its own line; total equals cap amount |

A zero-rounded entry is never silently dropped; it is shown for a human decision. Property tests (sum of lines equals total; no float operation anywhere) are added if a property library is approved. \[Approve\]

### 13.3 Security and abuse tests

Unauthenticated access to every route; two-workspace cross access on every route and ID parameter; malformed and oversize bodies; SQL injection strings; stored XSS strings in work item titles; prompt-injection corpus (instruction override, role claims, hidden text, requests for amounts); duplicate approval from two sessions at once; repeated invoice creation; approval then edit then execute; replayed idempotency key with changed body; seeded fake secret never present in logs, errors or prompts; removed-member session; expired approval; Slack signature and replay tests when section 10.2 is built.

### 13.4 End-to-end scenario

Create client; add project with contract and scope rules; connect a test repository; import work items; enter and approve time entries; run reconciliation; review AI suggestions; approve; create a draft invoice in provider test mode; verify the invoice read back and the audit report hash. Every step asserts persisted state, not only screen text.

### 13.5 Quality gates in CI

Type check, lint, unit and integration tests, migration up on an empty database and on the previous schema, build, dependency audit, secret scan, and a check that no source file imports the executor outside src/providers. A pull request cannot merge with any gate red. Every fixed bug adds a regression test where practical.

### 15.3 Frontend rules

1. The browser calls only the VendorProof API. No provider, Swytchcode or LLM call exists in frontend code.
2. Money is an integer plus an ISO currency code. A single MoneyText component formats it using the currency's minor digits; no floating-point parsing or arithmetic.
3. Types come from the shared Zod schemas in packages/shared, so request and response contracts have one source.
4. No secrets, tokens or workspace IDs in frontend variables; workspace comes from the session.
5. Provider-sourced text is rendered as plain text, never as HTML.
6. Lenis: kept as is on public pages. Inside the app, scrollable overlays, tables and dialogs carry the Lenis prevent attribute so nested scroll works; reduced-motion preferences are respected; page transitions never delay or hide a confirmation of a financial action. The exact Lenis setup is confirmed against the starter.
7. Server state uses a small fetch wrapper with typed results. Whether to adopt a data-fetching library is an open decision, and not adding one is the default. \[Approve\]

### 16.2 Core interfaces (descriptive, not provider schemas)

```ts
interface WorkSourceProvider {
  listWorkItems(ctx: WorkspaceContext, source: SourceRef, period: Period, cursor?: Cursor): Promise<Page<WorkItemDraft>>
  getWorkItem(ctx: WorkspaceContext, source: SourceRef, externalId: string): Promise<WorkItemDraft>

interface InvoiceProvider {
  createDraft(ctx: WorkspaceContext, cmd: CreateDraftCommand, key: IdempotencyKey): Promise<ExecutionResult<ProviderInvoiceRef>>
  readInvoice(ctx: WorkspaceContext, ref: ProviderInvoiceRef): Promise<ProviderInvoiceView>
  findByMetadata?(ctx: WorkspaceContext, meta: RunMetadata): Promise<ProviderInvoiceRef | null>
}

interface ReportStore { put(ctx: WorkspaceContext, report: ReportFile): Promise<StoredReportRef> }
```

findByMetadata exists only if a verified read method supports it. ExecutionResult carries the status ok, failed or unknown, so callers cannot confuse a timeout with a rejection.

### 16.3 Worker jobs

ingest-run, classify-run, render-report, upload-report, notify, create-draft-invoice, reconcile-pending-executions. Each job loads its run from the database, checks the state, and does nothing if the state no longer matches. create-draft-invoice has a retry limit of zero.

## 17. API route inventory and contracts

### 17.1 Conventions

- Base path /api/v1, JSON, UTF-8. Workspace is resolved from the session; no route accepts a workspace ID.
- Errors use one shape: code, message, correlationId, and optional details with field errors. Status codes: 401 not signed in, 404 missing or not yours, 409 version conflict or idempotency mismatch, 422 validation, 429 rate limit.
- Lists use cursor pagination with limit up to 100, ordered by a stable key.
- Mutating routes require the CSRF header; create-run, approve and cancel also require Idempotency-Key.
- Concurrency: a mutating run route takes the run version in the body and returns 409 on mismatch.
